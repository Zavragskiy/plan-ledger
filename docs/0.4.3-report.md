# plan-ledger 0.4.3 — дополнение к отчёту для потребителей

Релиз: <https://github.com/Zavragskiy/plan-ledger/releases/tag/v0.4.3>
Это продолжение [отчёта 0.4.2](0.4.2-report.md): два issue, открытые после установки, закрыты
в 0.4.3. Форматы задач не менялись, JSON `plan-status`/`plan-check` побайтово совпадает с 0.4.2
на том же состоянии плана.

## Что было в новых issue

- **#16 — «один шард на задачу» не получал выгоды от кэша 0.4.2.** Мемоизация считалась по паре
  `(БД, шард)`, поэтому план из 30 задач с 30 отдельными шардами по-прежнему стоил 30 вызовов
  `doit info` (~5.8 с). Это типичная форма «один этап — один контракт приёмки».
- **#15 — натуральный порядок работал только для `PREFIX-<число>`.** Id вида `D2-SCAN-PLAN` и
  `D10-LIVE` падали в строковое сравнение: `D10` шёл раньше `D2`. Отчёт 0.4.2 обещал «natural ID»
  без этого ограничения — читалось как дефект.

## Что сделано

- **Один вызов `doit` на команду.** `plan-status`, `plan-check` и `plan-shard list` берут состояние
  всех шардов из одного `doit list --status` (U/R/E), а `doit info` вызывают только для шардов,
  которым нужна подробность (stale/error). Чистый план — один процесс, а не один на шард.
- **Откаты сохранены.** Если `doit list` падает (сломанный `dodo.py`), команда идёт прежним путём
  через `info`; шард, которого нет в `dodo.py`, по-прежнему разрешается через `info` в `unknown`.
- **Натуральный id без ограничения формы.** Числовой сегмент сравнивается числом в любом месте id:
  `D2-SCAN-PLAN` < `D10-LIVE`, `TASK-8` < `TASK-13` < `TASK-1000`; id без цифр — детерминированный
  текстовый порядок. Ключ общий для `plan-status`, `plan-task list`, `plan-check` и будущего digest.

## Замеры

Синтетический план 30 задач / 30 шардов (по одной задаче на шард), Windows, Python 3.12, среднее
из двух прогонов, приёмка заселена `plan-run --all`.

| Команда | 0.4.2 | 0.4.3 |
| --- | --- | --- |
| `plan-status` | 5.8 с | 0.39 с |
| `plan-check` | 5.9 с | 0.35 с |

Для формы «60 задач / 2 шарда» из отчёта 0.4.2 цифра не выросла: ~0.5 с, потому что к одному
`list --status` добавляется `info` только для протухшего шарда.

Контроль эквивалентности: `plan-status --json` и `plan-check --json` побайтово совпали с 0.4.2
на смешанном плане (один stale-шард, один свежий) и на плане 30/30.

## Что стоит знать

- Смысловых изменений для скриптов нет: флаги, ключи JSON и вердикты те же, что в 0.4.2.
  Единственная видимая разница — порядок id с числовым сегментом после префикса (`D2-…` раньше
  `D10-…`).
- Крайний случай: план, где **все** шарды протухли (например, свежий clone без БД), стоит
  1 `list` + `info` на каждый протухший шард — столько же, сколько 0.4.2, плюс один вызов.
  В CI, где приёмка прогоняется перед гейтом, это ноль `info`.

## Тесты и CI

- pytest: 140 passed; новые тесты — один вызов на чистый план, `info` только за подробностью,
  откат при сломанном `list`, неизвестный шард, натуральный порядок `D2/D10`.
- CI: ubuntu/windows × Python 3.10/3.13, сборка колеса и smoke-install на теге.
